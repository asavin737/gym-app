# Проект: запись на групповые занятия

Рабочие заметки по репозиторию и [ЗАДАНИЕ.md](../ЗАДАНИЕ.md). Это контекст для реализации, не файл сдачи. Заметку «какие решения приняты и почему» задание просит отдельно, после кода.

Контракт восьми эндпоинтов в задании — источник истины по маршрутам, полям и кодам. Этот файл фиксирует предметную область и то, как устроен уже существующий код.

## Предметная область

Клуб проводит групповые занятия в залах. У занятия есть время начала, длительность, зал и вместимость. Клиент всегда имеет ровно один абонемент: число посещений и срок `validUntil` включительно. Клиента без абонемента в базе не бывает, такую ветку обрабатывать не нужно.

Запись клиента на занятие — отдельная бронь (`enrollment`). Одно место списывает одно посещение. В одной брони можно занять несколько мест (себя и гостей). На одно занятие у клиента может быть несколько броней, лимита на их число нет.

Занятие клуб может отменить. Новые записи на него закрыты, уже созданные брони остаются и должны быть видны клиенту. Занятия, залы и абонементы заводятся вне этого API.

Популярные занятия заполняются, поэтому есть лист ожидания. Когда мест меньше, чем просит клиент, он встаёт в очередь отдельным запросом. Освободившиеся при отмене места в той же операции достаются ожидающим по порядку постановки и превращаются в обычные активные брони без подтверждения клиента. Фоновой обработки для этого нет.

Объём, под который рассчитан клуб: сотни тысяч занятий и броней, данные только растут. Сидер этого репозитория такой объём не создаёт — см. ниже.

Занятие считается начавшимся, когда текущий момент не раньше `startsAt`. Длительность на это правило не влияет. Срок абонемента сравнивается с моментом запроса, а не с датой занятия.

Инварианты, которые обязаны держаться при любом решении в серых зонах контракта:

- занятых мест на занятии не больше вместимости;
- остаток посещений не уходит в минус;
- за одну бронь посещения списываются один раз.

Отказ не меняет ни места, ни остаток посещений.

## Что нужно добавить

В репозитории нет записи на занятия. Нужны восемь маршрутов без префикса `/api` и без версии, тесты на добавленный код и, при необходимости, миграции.

| Маршрут | Назначение |
|---|---|
| `POST /enrollments` | бронь, заголовок `Idempotency-Key`, списание мест и посещений |
| `POST /enrollments/{id}/seats` | новое итоговое число мест, не дельта |
| `POST /enrollments/{id}/cancel` | отмена, возврат посещений по правилам двух часов, продвижение очереди |
| `GET /enrollments/{id}` | карточка брони с занятием, залом и абонементом; можно из кэша |
| `GET /schedule` | занятия за период, постранично, непрозрачный `continuationToken` |
| `GET /analytics/load` | загруженность залов по дням, только роль `admin` |
| `POST /enrollments/waitlist` | встать в очередь, заголовок `Idempotency-Key` |
| `POST /enrollments/waitlist/{id}/cancel` | выйти из очереди |

Все восемь требуют JWT. В задании есть фраза «остальные пять эндпоинтов доступны любому авторизованному пользователю». Эндпоинтов восемь, и таблицы кодов оставляют роль только у загруженности залов. Ориентир — таблицы: любой авторизованный пользователь вызывает семь маршрутов, `GET /analytics/load` требует `admin`.

Чужая бронь и чужая запись очереди для владельца неотличимы от отсутствующей: `404`. Повтор отмены брони и повтор выхода из очереди возвращают `200` и ничего не меняют. Повтор создания с тем же ключом идемпотентности и тем же телом возвращает `201` и тело первой операции.

Лимит: не больше 60 запросов в минуту от одного пользователя суммарно по этим восьми маршрутам. `POST /auth/login` в лимит не входит.

.NET 9, nullable и implicit usings включены. Имена проектов, их расположение и команды из [README.md](../README.md) менять нельзя. Файлы и новые проекты добавлять можно.

| Проект | Роль |

| [DataAccessLayer](../DataAccessLayer) | `ClubDbContext`, сущности, конфигурации EF, репозитории, `UnitOfWork`, миграции, сидер |

Запуск: `docker compose up -d`, затем `dotnet run --project WebApi`. Приложение слушает `http://localhost:5080`, Swagger — `/swagger`, живость — `/health`. Миграции и сид выполняются при старте. Тесты: `dotnet test`, им нужны уже поднятые Postgres и Redis.

Postgres 16 на порту **5433**, база `club`, пользователь и пароль `club`. Redis 7 на порту **6380**. Строки подключения и `docker-compose.yml` не меняются. JWT и логирование лежат в [WebApi/appsettings.json](../WebApi/appsettings.json); срок токена 720 минут.

Стиль репозитория: без комментариев в коде. Исключение, которое вводит задание, — комментарий `// решение:` на одну-две строки там, где выбор не продиктован контрактом. [.editorconfig](../.editorconfig) и [.gitattributes](../.gitattributes) задают UTF-8, CRLF, отступ в 4 пробела для C# и file-scoped namespaces. Существующий код этому следует.

Пакеты, на которые уже опирается решение: EF Core 9.0.7, Npgsql 9.0.4, JWT Bearer 9.0.7, Swashbuckle 9.0.3, StackExchange.Redis 2.8.24, MSTest 3.9.3, `Microsoft.AspNetCore.Mvc.Testing` 9.0.7, Moq 4.20.72 (в тестах пока не используется). Локальный инструмент миграций — `dotnet-ef` 9.0.7, команда из README: `dotnet dotnet-ef migrations add <Name> --project DataAccessLayer --startup-project WebApi`.

## Модель данных, которая уже есть

Сущности анемичные: публичные свойства, никакой доменной логики.

- `User` — `Email`, `PasswordHash`, `Role` (`user` или `admin`), `CreatedAt`. Навигаций на абонемент и брони нет.
- `Room` — `Name`.
- `Class` — `RoomId`, `Title`, `StartsAt`, `DurationMinutes`, `Capacity`, `IsCancelled`, навигация на зал и коллекция броней.
- `Pass` — `UserId`, `RemainingVisits`, `ValidUntil` (`date`). Навигации на пользователя нет.
- `Enrollment` — `UserId`, `ClassId`, `Seats`, `Status` (строка), `CreatedAt`, `CancelledAt`, обязательная навигация `Class`. Навигации на пользователя нет.

Таблицы и колонки в snake_case: `users`, `rooms`, `classes`, `passes`, `enrollments`. Ключи — `bigint identity`. Все внешние ключи с `ON DELETE CASCADE`.

Индексы начальной миграции: `classes.room_id`, `enrollments.class_id`, `enrollments.user_id`, `passes.user_id`. Уникальности нет ни на `users.email`, ни на `passes.user_id`. Нет индекса по `classes.starts_at` и нет индекса по статусу брони. Проверочных ограничений на статус, вместимость и остаток посещений нет. Токена конкуренции (`xmin`, rowversion) нет.

`Enrollment.Status` в сидере принимает только `active` и `cancelled`. Отдельной таблицы листа ожидания нет, таблицы идемпотентности нет.

В [ClassConfiguration](../DataAccessLayer/Configurations/ClassConfiguration.cs) висит глобальный фильтр `HasQueryFilter(x => !x.IsCancelled)`. Обычные запросы к `Class` отменённые занятия не возвращают. У брони навигация на занятие обязательная, поэтому EF Core при выборке броней с этой навигацией отбрасывает и сами брони отменённых занятий. Карточка такой брони по контракту обязана отдаваться, а запись на отменённое занятие обязана завершаться `409` и `class-cancelled`, а не `404`. Эти пути читают занятие через `IgnoreQueryFilters()`.

`ClassRepository.GetWithEnrollmentsAsync` делает `Include` всех броней занятия. На сотнях тысяч строк так вместимость считать нельзя: нужен агрегат `SUM` по активным броням.

## Доступ к данным

[GenericRepository](../Common/Database/Repositories/Generic/GenericRepository.cs) даёт `Query()` (`IQueryable`), `GetByIdAsync`, `GetAllAsync`, `AnyAsync`, `CountAsync`, `CreateAsync`, `Update`, `Delete`.

Поверх него:

- `EnrollmentRepository.GetByUserAsync` — все брони пользователя, без фильтра по статусу и без `Include`;
- `ClassRepository.GetWithEnrollmentsAsync` — занятие с коллекцией броней, с учётом глобального фильтра;
- `PassRepository.GetByUserAsync` — `FirstOrDefault` по `UserId`;
- `RoomRepository` — без собственных методов;
- пользователя в `IUnitOfWork` нет, логин берёт `GetRepository<User>()`.

[UnitOfWork](../DataAccessLayer/UnitOfWork/UnitOfWork.cs) только раздаёт репозитории и вызывает `SaveChangesAsync`. Отдельного API транзакции нет. Транзакция пишется через `ClubDbContext.Database` внутри того же scoped-контекста, которым уже владеет unit of work.

Конфигурации подключаются сборкой: `ApplyConfigurationsFromAssembly`.

## Сиды

[DatabaseSeeder](../DataAccessLayer/Seeding/DatabaseSeeder.cs) выходит сразу, если в `users` уже есть строка. Повторный запуск не дополняет данные. Состав и количество начальных данных менять нельзя. Новые колонки своей схемы заполняются осмысленными значениями в этом же сидере.

Генератор — `Random(20260101)`. «Сейчас» — `UtcNow`, усечённый до минуты, на момент первого запуска. Время занятий привязано к этому моменту: пересоздание базы (`docker compose down -v`) сдвигает расписание. В тестах база создаётся заново на каждый прогон `dotnet test`, поэтому смещения сида внутри одного прогона стабильны. Давно поднятая dev-база к текущим минутам уже не привязана.

Объёмы сида, в отличие от «сотен тысяч» в тексте задания:

- 10 залов, `Hall A` … `Hall K` без `Hall I`;
- 200 пользователей `user001@club.test` … `user200@club.test` с ролью `user` и 5 админов `admin001@club.test` … `admin005@club.test`;
- пароль у всех один: `Password123!`;
- 205 абонементов, по одному на пользователя и на админа;
- 200 занятий;
- цикл до 250 попыток брони, часть активных попыток пропускается, плюс отдельные добивки залов.

Абонемент считается от позиции пользователя, начиная с 1:

- остаток от деления позиции на 20 равен 0 — 0 посещений;
- остаток равен 10 — 1 посещение;
- иначе 10…40 посещений;
- позиция кратна 17 — срок уже истёк (от 1 до 30 дней назад);
- иначе срок от 30 до 180 дней вперёд.

Занятия: старт `now + (i - 100) * 432` минут, то есть примерно от 30 дней назад до 30 дней вперёд, шаг 7,2 часа. При `i > 0` и `i % 40 == 0` старт совпадает с предыдущим занятием. Длительность по кругу 45, 60, 90. Вместимость 8…30. Зал — `i % 10`. Название — одно из десяти по кругу. `IsCancelled` у индексов, кратных 13: id 1, 14, 27 и далее.

Отдельно id 151–155 (индексы 150–154) ставятся на +20, +50, +80, +100 и +115 минут от сида и помечаются неотменёнными.

Брони случайного цикла садятся только на `user001`…`user200`, не на админов. Мест в попытке 1…3. Попытка с индексом, кратным 5, создаётся как `cancelled` и не списывает посещения. Активная попытка пропускается целиком, если не хватает мест или посещений. Затем шесть будущих неотменённых занятий со стартом позже чем через 3 часа добиваются до 0, 0, 1, 1, 2 и 2 свободных мест. Донором добивки может стать и админ: поиск идёт по всем абонементам. Ещё три занятия со стартом позже чем через сутки получают у одного донора две активные брони по одному месту, если вместимость позволяет. Это готовые случаи «несколько броней одного клиента на одно занятие».

`CreatedAt` брони всегда раньше и старта занятия, и момента сида. `CancelledAt` лежит между созданием и стартом.

## Авторизация

`POST /auth/login` принимает email и пароль и возвращает `accessToken` и `expiresAt`. Неверный email или пароль — пустой `401` через `Unauthorized()`. Это служебный ответ, его формат задание менять не просит.

Токен подписывается HMAC-SHA256. Проверяются issuer, audience, срок и подпись, `ClockSkew = TimeSpan.Zero`. Claims: `ClaimTypes.NameIdentifier` — id пользователя, `ClaimTypes.Name` — email, `ClaimTypes.Role` — роль. [BaseApiController](../WebApi/Controllers/BaseApiController.cs) уже читает `CurrentUserId` и `IsAdmin` (`admin`). `AuthController` от него не наследуется.

Идентификатор пользователя в новые маршруты не передаётся: только токен. Запрос без токена или с недействительным токеном — `401`, и этот код в таблицах задания не повторяется.

`Program` включает `ValidateScopes` и `ValidateOnBuild`. Перед `Run` контейнер принудительно резолвит `IConnectionMultiplexer`, поэтому процесс без Redis не стартует, даже хотя `/health` зависимости не опрашивает. Swagger включён всегда, не только в Development.

## Ошибки и JSON

[ExceptionHandlingMiddleware](../WebApi/Middleware/ExceptionHandlingMiddleware.cs) ловит необработанное исключение и пишет `ProblemDetails` со статусом 500 и title `Internal server error`. Если клиент отменил запрос, middleware завершается молча. Если ответ уже начат, исключение пробрасывается дальше. Своих бизнес-ошибок middleware не знает.

`AddProblemDetails()` уже подключён. Поле `reason` у `409` — свойство верхнего уровня рядом со `status` и `title`. Встроенный writer выносит `ProblemDetails.Extensions` на верхний уровень.

Тело успеха содержит ровно перечисленные поля. Неизвестные поля запроса игнорируются: так уже делает System.Text.Json по умолчанию, имена в JSON — camelCase. Моменты времени — UTC, ISO 8601. Значение без смещения считается UTC, со смещением приводится к UTC. Поля-даты (`pass.validUntil`, `items[].date`, `from` и `to` загруженности) — календарная дата `2026-09-22`; значение с временем на входе — `400`.

Нечисловой идентификатор в пути или в теле — `400`. Число, которого нет в базе, — `404`. Ограничение маршрута `{id:long}` само по себе превращает нечисловой сегмент в `404`, потому что маршрут не совпадает. Для контрактных `400` идентификатор в пути разбирается своим кодом.

Колонки времени — `timestamp with time zone`. Раундтрип .NET и Postgres расходится на долях микросекунды, и один и тот же `createdAt` из памяти и из базы может отличаться. Задание само приводит усечение времени как пример решения, которое помечается `// решение:`.

## Кэш

[ICacheService](../Common/Caching/ICacheService.cs) — get, set, remove поверх Redis. Сериализация `JsonSerializerDefaults.Web`. TTL по умолчанию — 5 минут, его можно переопределить на вызове. Реализация принимает `CancellationToken` и не передаёт его в StackExchange.Redis. Сейчас кэш никто не вызывает.

Приложение смотрит в Redis DB 0. Тесты подменяются на DB 1 и один раз промывают её на старте сборки.

По заданию из кэша может отдаваться только карточка брони. После операций этого API клиент видит актуальные данные. Правки базы мимо API отслеживать не нужно. В карточке лежит `pass.remainingVisits`, общий для всех броней пользователя: сброс одной карточки оставляет остальные с прежним остатком.

## Тесты

[TestDatabase](../WebApi.Tests/TestDatabase.cs) на `AssemblyInitialize` создаёт базу `club_tests_{guid}` и на `AssemblyCleanup` удаляет её `WITH (FORCE)`. Строку сервера можно подменить переменной `TEST_POSTGRES`, Redis — `TEST_REDIS`. Иначе берутся localhost:5433 и localhost:6380, DB 1.

[ApiApplicationFactory](../WebApi.Tests/ApiApplicationFactory.cs) поднимает приложение в среде `Testing` и подменяет обе строки подключения. Стартап сам вызывает `MigrateAsync` и `SeedAsync`. На весь прогон одна база и один набор сидов. Атрибута параллельного запуска у сборки нет, MSTest по умолчанию гоняет тесты последовательно, но отката между методами нет: следующий тест видит записи предыдущего.

Покрываются контроллеры, добавленные методы репозиториев и собственные сервисы. Проверяющий запускает решение командами README без дополнительных шагов.

## Паттерны, которые уже применяются

Это слоистый transaction script.

- HTTP остаётся тонким: существующий логин сам ходит в unit of work и в `PasswordHasher`.
- Доменные типы — анемичные POCO с интерфейсом `IEntity` (`long Id`). Агрегатов, value object-ов, доменных событий и инвариантов внутри сущностей нет.
- Доступ к данным — generic repository плюс узкие репозитории на `DbSet`. Unit of work не открывает транзакцию и не публикует события.
- Схема описана `IEntityTypeConfiguration`, не атрибутами на сущностях.
- Скрытие отменённых занятий — глобальный query filter EF, а не спецификация в домене.
- Ошибки инфраструктуры — middleware и `ProblemDetails`.
- Кэш — один интерфейс над Redis, без декораторов репозиториев и без инвалидации.
- Сидер — статический класс с ранним выходом, не отдельный профиль миграции.
- Состав приложения — classic ASP.NET Core host в `Program.cs`, DI с проверкой scope на сборке контейнера.

Этого набора достаточно для восьми эндпоинтов. Рядом с ним появляются транзакция, блокировка строк занятия и абонемента, агрегаты по броням и инвалидация карточки. Это продолжение текущего стиля, а не смена архитектуры.

## DDD, CQRS и outbox

Их в репозитории нет, и задание их не задаёт.

**DDD.** Нет границы агрегата «занятие + брони + абонемент», нет репозитория агрегата, нет единого языка в типах: статус брони — строка, роль — строка, места и посещения — голые `int`. Инварианты вместимости и остатка сейчас держатся только аккуратностью сидера. Перенос правил в методы сущностей возможен локально, но переписывать решение в агрегаты, доменные события и слой application/domain не нужно: проверяющий собирает текущие проекты, а готовый код уже анемичный.

**CQRS.** Нет команд, запросов, MediatR, отдельных read-моделей и шин. Чтение и запись идут в один `ClubDbContext`. Расписание и загруженность — обычные запросы к тем же таблицам. Делить модель на write и read ради отчёта по залам не из чего: отчёт и так считается SQL-агрегатом по занятиям и активным броням.

**Outbox.** Нет таблицы исходящих сообщений, брокера и фонового воркера. Продвижение очереди и возврат посещений происходят в запросе отмены, в той же транзакции, что и освобождение мест. Задание прямо говорит, что фоновую обработку для очереди и для возврата при отмене занятия клубом писать не нужно. Outbox появился бы только вместе с сообщениями, которых в контракте нет.
