# Чеклист реализации

Порядок работ по восьми эндпоинтам. Контракт — в [ЗАДАНИЕ.md](ЗАДАНИЕ.md), устройство кода — в [.cursor/rules/PROJECT.md](.cursor/rules/PROJECT.md), куда класть новое — в [ARCHITECTURE.md](ARCHITECTURE.md).

Открытое решение из архитектуры закрывается комментарием `// решение:` рядом с кодом. Пункты [OUT_OF_SCOPE.md](OUT_OF_SCOPE.md) сюда не входят. Тесты сценария пишутся в его фазе, в `WebApi.Tests`, на общей базе прогона.

## Фаза 1. Каркас

- [ ] 1. Ответы сценариев собираются как `ProblemDetails`, `reason` кладётся в `Extensions`.
- [ ] 2. Идентификатор в пути разбирается своим кодом и даёт `400` на нечисловое значение, без ограничения маршрута `:long`.
- [ ] 3. Моменты без смещения приводятся к UTC, поля-даты отклоняют значение с временем.
- [ ] 4. Квант `createdAt` выбирается и помечается `// решение:`, чтобы ответ создания и повторное чтение совпадали.
- [ ] 5. Контроллеры броней, расписания и загруженности наследуют [BaseApiController](WebApi/Controllers/BaseApiController.cs) и требуют JWT. Роль проверяется только на `GET /analytics/load`.
- [ ] 6. Сценарий открывает транзакцию через `DbContext` существующего `IUnitOfWork`. Отказ откатывает её целиком.

## Фаза 2. Схема и запросы

- [ ] 7. Модель очереди выбирается и помечается `// решение:`. Запись очереди не читается как бронь, маршруты отмены брони и выхода из очереди остаются разными.
- [ ] 8. Идемпотентность хранится в той же транзакции, что и бронь или очередь. Область ключа и поведение при том же ключе с другим телом помечаются `// решение:`. Своего предела длины ключа нет.
- [ ] 9. Миграция командой из README: очередь, идемпотентность, индексы по `starts_at`, статусу брони и порядку очереди. Имена существующих таблиц и колонок сохраняются. Миграция заполняет новые колонки уже существующих строк.
- [ ] 10. [DatabaseSeeder](DataAccessLayer/Seeding/DatabaseSeeder.cs) заполняет новые данные на пустой базе. Число пользователей, залов, занятий и броней не сокращается.
- [ ] 11. В репозитории добавляются методы: занятие и бронь с `IgnoreQueryFilters()`, блокировка строки занятия и абонемента, сумма мест активных броней. `GetWithEnrollmentsAsync` для вместимости не используется.

## Фаза 3. POST /enrollments

- [ ] 12. `seats` меньше единицы, пустой `Idempotency-Key` и неверный формат дают `400`. Неизвестные поля тела игнорируются.
- [ ] 13. Повтор с тем же ключом и тем же телом возвращает `201` и тело первой брони. Другое тело обрабатывается по решению из задачи 8.
- [ ] 14. Создание списывает места и посещения. Причины `409`: `capacity-exceeded`, `pass-exhausted`, `pass-expired`, `class-started`, `class-cancelled`. Отсутствующее занятие — `404`, отменённое клубом — `409`, а не `404`.
- [ ] 15. Отказ не оставляет брони, списания и ключа. В очередь этот маршрут не ставит.
- [ ] 16. Тесты контроллера, методов репозитория и сервиса на успех, отказы и идемпотентность.

## Фаза 4. GET /enrollments/{id}

- [ ] 17. Карточка отдаёт бронь, занятие, зал и абонемент ровно с полями контракта, включая отменённую бронь и бронь на отменённое занятие.
- [ ] 18. Чужая и отсутствующая бронь — `404`.
- [ ] 19. Чтение может идти из `ICacheService`. После операций API сбрасываются карточки всех пользователей, чья бронь или остаток посещений изменились.
- [ ] 20. Тесты карточки, `404` и актуальности кэша после записи.

## Фаза 5. POST /enrollments/{id}/seats

- [ ] 21. Новое число мест — итог, не дельта. Проверки `400` и `404` как в контракте.
- [ ] 22. Увеличение требует места и посещения. Уменьшение возвращает разницу и разрешено при просроченном или исчерпанном абонементе. То же число мест проходит проверки и возвращает `200` без изменений.
- [ ] 23. Причины `409`: `capacity-exceeded`, `pass-exhausted`, `pass-expired`, `class-started`, `class-cancelled`, `enrollment-cancelled`. Ответ `200` — полная карточка. Кэш затронутых карточек сбрасывается.
- [ ] 24. Тесты увеличения, уменьшения, пустого изменения и каждого отказа.

## Фаза 6. Лист ожидания

- [ ] 25. `POST /enrollments/waitlist` ставит в очередь, не списывая посещения и не проверяя абонемент. Причины `409`: `seats-available`, `already-waiting`, `class-started`, `class-cancelled`. Идемпотентность как у записи. `position` считается среди ожидающих, с единицы.
- [ ] 26. `POST /enrollments/waitlist/{id}/cancel` убирает из очереди. Повтор возвращает `200` и ничего не меняет. Ушедший место позже не получает, стоявшие за ним поднимаются. Чужая запись — `404`.
- [ ] 27. Тесты постановки, отказа, идемпотентности, выхода и повторного выхода.

## Фаза 7. POST /enrollments/{id}/cancel

- [ ] 28. Места освобождаются всегда, когда отмена проходит. За два часа и больше посещения возвращаются полностью, меньше двух часов — `refundedVisits` равен нулю. Отмена занятия клубом возвращает посещения полностью, в том числе после начала. Повтор возвращает тот же `200`.
- [ ] 29. `409` с `class-started` только у ещё действующей брони на неотменённое начавшееся занятие.
- [ ] 30. Освободившиеся места раздаются ожидающим в этой же транзакции и становятся активными бронями. Списание посещений у ожидающего одно. Две развилки помечаются `// решение:`: очередь не помещается в освободившийся остаток или у ожидающего не хватает абонемента; занятие уже отменено клубом. Невозможность продвинуть очередь не меняет ответ отмены.
- [ ] 31. Сбрасываются карточки отменившего и тех, чьи брони созданы из очереди.
- [ ] 32. Тесты сроков возврата, повтора, инвариантов мест и посещений и продвижения очереди.

## Фаза 8. GET /schedule

- [ ] 33. `from` включительно, `to` строго позже и не включается, `limit` 1…100 и по умолчанию 20. Битый токен, плохие даты и `roomId` — `400`. Неизвестный зал даёт пустой список.
- [ ] 34. Страница считается SQL-агрегатом: без отменённых занятий, по возрастанию `startsAt`, `freeSeats` не ниже нуля, `mySeats` — сумма активных мест текущего пользователя. Формат `continuationToken` помечается `// решение:`.
- [ ] 35. Тесты периода, фильтра зала, страниц и пустого хвоста.

## Фаза 9. GET /analytics/load

- [ ] 36. Даты `from` и `to` включительны, значение с временем — `400`. Роль не `admin` — `403`. Неизвестный зал даёт пустой список.
- [ ] 37. Строка только для дня и зала, где были неотменённые занятия. Отменённые брони не входят в `bookedSeats`. Порядок — дата, затем id зала.
- [ ] 38. Тесты доступа, пустых дней, отменённых занятий и броней.

## Фаза 10. Лимит частоты

- [ ] 39. Счётчик в Redis через уже зарегистрированный `IConnectionMultiplexer`: не больше 60 запросов в минуту на пользователя по восьми маршрутам. Вид окна помечается `// решение:`. `POST /auth/login` не считается.
- [ ] 40. Шестьдесят первый запрос — `429` в виде `ProblemDetails`.
- [ ] 41. Тесты порога, раздельности пользователей и того, что логин лимит не тратит.
